# ADR-0002: Letterbox 640×640

## Статус
Accepted (V1.0)

## Контекст
YOLOv8/YOLO11 на входе требует фиксированный размер тензора (обычно 640×640).
Датасет-изображения — произвольного размера (1920×1080, 800×600, 1024×1024…).
Bounding-box и keypoints в БД хранятся **нормализованными** (0..1).

Нужно выбрать способ приведения картинки к 640×640, при котором:

* координаты рамок остаются консистентными,
* нет искажений aspect ratio (это критично для pose-модели),
* можно восстановить координаты в исходной картинке (для экспорта).

## Решение
Letterbox — масштабирование с сохранением aspect ratio и паддингом серым
(`LETTERBOX_FILL = (114,114,114)`) до 640×640. Реализация — в
`services/file_service.letterbox()`.

Оригинальные `original_width/original_height` сохраняются в БД
(`ImageModel.original_width/height`, миграция Stage 1) для обратного
пересчёта. Метаданные letterbox-трансформации экспортируются в
`dataset_meta.json` (галочка в UI «Include metadata»).

## Последствия
+ Нет искажений — поза и bbox сохраняют пропорции.
+ Единый формат входа для YOLO/detect и YOLO/pose.
+ `dataset_meta.json` позволяет распаковать координаты обратно в исходный
  размер (scale, pad_x, pad_y).
− Бесполезный «серый» регион по краям для не-квадратных фото. Модель
  видит меньше полезных пикселей. Обычно это OK, но для очень вытянутых
  кадров (панорамы) возможна потеря качества.
− Пустоты (padding) — часть входа модели. Auto-blur должен игнорировать
  её (за это отвечает фильтр `bw*bh > 0.95` в `auto_blur_service`).

## Альтернативы
1. **Resize-stretch** — быстро, но искажает пропорции. Для pose-модели
   неприемлемо.
2. **Pad-to-divisible** (YOLO внутренний) — не работает вне YOLO, нельзя
   воспроизвести при экспорте.
3. **Dynamic input** (`imgsz=0`) — медленнее и хуже для CPU-инференса,
   требует пересчёта bbox на каждом кадре.
