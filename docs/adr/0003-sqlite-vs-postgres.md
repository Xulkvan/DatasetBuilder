# ADR-0003: SQLite vs PostgreSQL

## Статус
Accepted (V7.5.0 → V14.2.0)

## Контекст
Изначально проект использовал MySQL. Это создавало барьер входа:

* нужно устанавливать MySQL-сервер (или Docker-контейнер),
* управлять пользователями и паролями,
* для Windows-пользователей это особенно болезненно.

Одновременно командный режим (Team Edition) требует настоящей БД с
конкурентным доступом и транзакциями, чтобы 5–20 человек могли работать
одновременно без «database is locked».

## Решение
Два поддерживаемых движка:

1. **SQLite** (default для соло) — единый файл `data/dataset.db`,
   WAL-журнал, `busy_timeout=30s`, `synchronous=NORMAL`.
   Настраивается через `DB_ENGINE=sqlite DB_PATH=...`.
2. **PostgreSQL** (для команды) — `DB_ENGINE=postgres`, полноценные
   сессии, `pool_size=10`, `pool_pre_ping`.

Также поддерживается MySQL (историческая совместимость + миграция
MySQL→SQLite встроена в UI).

`AUTH_MODE=auto` автоматически ставит `local` для SQLite и `team` для
Postgres/MySQL.

## Последствия
+ Нулевая установка для соло (файл рядом с приложением).
+ Backup SQLite = копирование файла (VACUUM INTO).
+ Postgres для команды даёт MVCC и настоящий параллелизм.
+ Одна SQLAlchemy-модель (`models.py`) работает с обоими движками.
− SQLite: конкурентные записи блокируются. Ограничение ~10 одновременных
  писателей; для 20+ человек нужен Postgres.
− SQLite: нет `FOR UPDATE`, `save_annotations` использует WAL как
  компромисс. В team mode предпочтителен Postgres.
− Разные типы `TINYINT(1)` vs `SMALLINT` → миграции через `ensure_schema`
  с адаптацией DDL под движок.

## Альтернативы
1. **Только Postgres** — отклонено: тяжёлый setup для соло-сценария.
2. **Только MySQL** — отклонено: те же проблемы установки + license.
3. **DuckDB** — отклонено: OLAP, не OLTP; нет ORM-поддержки на уровне
   SQLAlchemy 2.0.
