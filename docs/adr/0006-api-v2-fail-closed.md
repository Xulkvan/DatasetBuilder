# ADR-0006: API v2 fail-closed

## Статус
Accepted (Stage 1, F-01)

## Контекст
API v2 (`/api/v2/*`) использует Bearer-авторизацию через `API_KEY`.
До фикса проверка `_v2_api_key_guard` и `require_api_key` пропускали
запросы, если `API_KEY` не задан в окружении («auth disabled»).
Это создавало S1-байпас: любой, у кого есть сетевой доступ, мог
читать/изменять датасеты через `/api/v2/*` без аутентификации.

## Решение
Fail-closed: если `API_KEY` пуст или не задан → `/api/v2/*` отвечает
`503 Service Unavailable` с `detail.key = "error.apiV2Disabled"`.

Единая точка проверки — `services/api_key.py::validate_api_key`:
  * пустой `API_KEY` → 503;
  * нет заголовка `Authorization: Bearer ...` → 401;
  * токен не совпадает (`secrets.compare_digest`) → 403.

Вызывается в двух местах (defense-in-depth):
  1. Middleware `_v2_api_key_guard` в `app.py`;
  2. Dependency `require_api_key` в `routers/api_v2.py`.

## Последствия
+ Невозможно случайно оставить v2 открытым в проде.
+ Ошибка конфигурации видна сразу (503), а не через «тихую» утечку.
− Если `API_KEY` действительно не нужен (air-gapped демо) — придётся
  задать любой непустой токен. В README и `.env.example` — явное
  предупреждение.

## Альтернативы
1. Fail-open (оставить как было) — отклонено: S1.
2. Автогенерация `API_KEY` при старте — отклонено: непредсказуемость
   для клиентов, которые не знают токен. Пользователь должен задать
   сам.
3. Отключить `/api/v2/*` при пустом `API_KEY` полностью (404) —
   отклонено: 503 информативнее (сервер жив, фича выключена).
